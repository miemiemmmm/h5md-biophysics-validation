# Technical validation of the H5MD `biophysics` metadata schema

This technical validation associates with the H5MD `biophysics` metadata schema with its publication entitled "A Hierarchical Metadata Schema for Self-Contained Molecular Dynamics Trajectory Archives".
This directory holds everything needed to reproduce the Technical Validation in its supplementary information (`SI-technical-validation`). 
The specification (`SI-specification.pdf` in the supplementary material), version 1.0.0-alpha.1 of the `biophysics` module (files stamped `version = [1, 0]`), is the normative source of the schema model (`h5md_validator/spec.py`) of the validator maintained with the specification in [gromacs/h5md-biophysics](https://gitlab.com/gromacs/h5md-biophysics/-/tree/v1.0.0-alpha.1/validator); this repository installs that validator rather than keeping a copy. 
By generating the H5MD outputs from the GROMACS reference implementation, the validation suite can compare them against the schema model to identify any discrepancies.
Where the two disagree, the disagreement is reported as a finding rather than absorbed into the model.

## The six validations

| | Question | Artifact | Details |
|:--|:--|:--|:--|
| 1 | Can the schema represent the metadata of realistic MD systems? | `coverage.json`, `parameter_surface.json` | [details](docs/validations.md#validation-1--schema-coverage) |
| 2 | Does serialising and parsing preserve it? | `roundtrip.json`, `interaction_coverage.json` | [details](docs/validations.md#validation-2--round-trip-fidelity) |
| 3 | Is a file internally consistent? | `conformance.json` | [details](docs/validations.md#validation-3--internal-consistency) |
| 4 | Are invalid files detected? | `negative_tests.json` | [details](docs/validations.md#validation-4--negative-tests) |
| 5 | What does the metadata cost to store and to write? | `storage.json`, `data/decompose_run*.json` | [details](docs/validations.md#validation-5--what-the-metadata-costs-to-store-and-to-write) |
| 6 | Do other engines' parameters map onto the same concepts? | `amber_interop.json` | [details](docs/validations.md#validation-6--cross-engine-interoperability) |

Fidelity and coverage are kept apart throughout. A file can carry back everything
it holds without change and still have come from a source the schema could not
fully represent; conflating the two would let a coverage gap read as a success.

## Setup

The following three environment variables are needed by the validation steps.
Download the validation dataset from Zenodo record [10.5281/zenodo.23399239](https://doi.org/10.5281/zenodo.23399239) and unpack it. 
Set the `H5MD_VALIDATION_DATA` environment variable to point at the extracted directory.
The reference data files and result artifacts generated by the validation steps will be put to 
the `_data` (`.tpr`, `.mdp`, output `.h5md`, etc.) and `_results` (`.json`, figures) sub-directories
in the `$H5MD_VALIDATION_DATA`. `DATA_DIR` and `RESULTS_DIR` override either location; if the dataset
directory is not writable, both default to `h5md_validation/` under the system temporary directory.
`run_all.sh` prints the locations it uses.
Python requires the following packages: `h5py`, `numpy`, `matplotlib` (optional for validation 5), `scipy` (optional, for `scripts/fit_write_time.py`), and `pytraj` (optional for validation 6, which is skipped without it; pytraj is part of AmberTools), plus the validator from the specification repository (Validations 1, 3 and 4).
`environment.yml` creates such an environment, validator included (`micromamba create -f environment.yml`); to add the validator to an existing environment instead:

```bash
$PY_EXE -m pip install "h5md-biophysics-validator @ git+https://gitlab.com/gromacs/h5md-biophysics.git@v1.0.0-alpha.1#subdirectory=validator"
```

```bash
export H5MD_VALIDATION_DATA=/path/to/validation_systems
export PY_EXE=/path/to/python/env/bin/python
export GMX_BIN=/path/to/gromacs/bin/gmx        # reference GROMACS implementation with the biophysics schema (gromacs-biophysics-metadata.zip)
```

## Quick start

```bash
bash scripts/run_all.sh --generate   # build the reference files first (hours)
bash scripts/run_all.sh              # analysis only, reference files must exist
```

`--generate` builds every (system, protocol) pair with `NTOMP` OpenMP threads per run (default 8).
To try the chain on a few pairs first, build only those and run the validations one by one, as described in [docs/validations.md](docs/validations.md#build-the-reference-files).

Results go to `$H5MD_VALIDATION_DATA/_results`. Each step of the chain is described in [docs/validations.md](docs/validations.md), and the numbers a full run reproduces are listed under [Expected results](docs/validations.md#expected-results).

## Validating a single file

With the validator installed as above:

```python
from h5md_validator import validate
report = validate("trajectory.h5md")
print(report.summary())
for finding in report.errors:
    print(finding)
```

`report.conformant` is true when no ERROR-level finding was raised. Findings
come at three levels: `ERROR` (violates a MUST of the specification), `WARNING`
(violates a SHOULD), and `INFO`.

Finding codes are listed in [docs/check-codes.md](docs/check-codes.md).
